# B1–B7 · Linux, containers, lab foundations

Seven sessions. At the end you have a working containerlab install, two vendor NOSes booting, and — the part that matters — you understand what containerlab is doing to the kernel, because you did it by hand first at B3.

**Do not skip B3 to get to B5 faster.** Every lab from B5 to D95 runs on veth pairs and network namespaces. Engineers who never built one by hand debug containerlab by restarting it.

---

## B1 · Linux CLI and the `ip` command family

*Session 1 — Sat 8 Aug, the 180-minute slot. Use the extension.*

**Why this day exists**
Every verification step from B5 to D95 happens at a Linux shell — inside a container, inside a namespace, or on the host. `ip` and `tcpdump` are the two tools you will type more than any vendor CLI, including Junos.

**Objective**
*Say out loud:* what `ip route get` computes that `ip route show` cannot, and why that difference matters when a route exists but traffic still doesn't flow.

**Source — 60 min**

| Time | What | Where |
|---|---|---|
| 15 min | `man ip` — read the OBJECT list and stop. You are learning the shape of the command, not memorising it | `man ip` |
| 25 min | iproute2 reference — the `link`, `address`, `route`, `neighbour` sections | https://baturin.org/docs/iproute2/ |
| 20 min | `man tcpdump` — the FILTER section, plus `-n`, `-e`, `-i`, `-w`, `-r` | `man tcpdump` |

**Do — 120 min**

1. `ip -br link` · `ip -br addr` · `ip -c route`. The `-br` and `-c` forms are the ones worth muscle memory.
2. `ip route show` then `ip route get 1.1.1.1`. Write down every field `get` returns that `show` did not. Source address selection is the one to notice.
3. Build and tear down an interface end to end:
   ```
   ip link add dummy0 type dummy
   ip link set dummy0 up
   ip addr add 192.0.2.1/24 dev dummy0
   ip route add 198.51.100.0/24 via 192.0.2.2 dev dummy0
   ip route get 198.51.100.5
   ip link del dummy0
   ```
   Note what happened to the route when the link went away, and why nothing had to delete it explicitly.
4. `ip neigh show`. Ping something on your LAN, watch the entry appear. `ip neigh del` it, ping again, watch it repopulate. `ip -s neigh show` for the state machine — `REACHABLE`, `STALE`, `FAILED`.
5. `tcpdump -ni <iface> icmp` in one terminal, `ping` in another. Then re-run with `-e` and read the Ethernet header. Then `-w /tmp/b1.pcap`, and `-r` it back.
6. `ip -s link show <iface>` — find the error and drop counters. At D17 and D95 you will be converting drop counts into milliseconds of outage; this is where those counts come from.

**Weekend extension — 30 min**
`ip route add ... metric` two routes to the same destination with different metrics. Confirm with `ip route get` which one wins. This is the kernel's version of the tie-break logic you will write from memory at B29.

**Done when**
- [ ] Dummy interface created, addressed, routed through, and removed — no notes
- [ ] The `get` vs `show` difference stated in one sentence
- [ ] A pcap written and read back. **Do not commit it** — `.gitignore` covers `*.pcap`; confirm with `git status`
- [ ] Journal entry names one thing you had to look up

**Cards touched** — CP-11

## B2 · Docker fundamentals

**Why this day exists**
containerlab is a Docker orchestrator. Every "the lab won't come up" problem from B5 onward is a Docker problem wearing a networking costume.

**Objective**
*Say out loud:* what `--network host`, `bridge`, and `none` each do to a container's network namespace, and which one containerlab needs.

**Source — 45 min**

| Time | What | Where |
|---|---|---|
| 20 min | Docker networking overview — bridge, host, none, and what a user-defined bridge adds | https://docs.docker.com/engine/network/ |
| 15 min | `docker run --help` — focus on `--network`, `--privileged`, `--cap-add`, `-v` | `docker run --help` |
| 10 min | Images vs containers vs layers — enough to know why `docker pull` is slow once and fast after | https://docs.docker.com/get-started/docker-concepts/the-basics/ |

**Do — 45 min**

1. `docker run -d --name t1 alpine sleep 3600`. Then `docker exec -it t1 sh`. Inside: `ip -br addr`. Note the address and where it came from.
2. On the **host**, `ip -br link`. Find the `veth...` interface that appeared when the container started. That veth's other end is inside the container — this is the whole trick, and B3 builds it by hand.
3. `docker network inspect bridge` — find the subnet, the gateway, and your container in the containers list.
4. Run the same image three ways and compare `ip -br addr` inside each:
   ```
   docker run --rm -it --network bridge alpine ip -br addr
   docker run --rm -it --network host   alpine ip -br addr
   docker run --rm -it --network none   alpine ip -br addr
   ```
   One of these shows you the host's interfaces. Understand why that is a problem for a lab of twelve routers.
5. Enter a container's namespace from the host without `docker exec`:
   ```
   pid=$(docker inspect -f '{{.State.Pid}}' t1)
   nsenter -t $pid -n ip -br addr
   ```
   This is how containerlab configures nodes, and how you will debug them when `exec` is unavailable.
6. `docker logs`, `docker inspect`, `docker rm -f t1`. Then `docker system df` — know where the disk goes before vendor images arrive at B6.

**Done when**
- [ ] The host-side veth for a running container identified by name
- [ ] `nsenter` used to read a container's interfaces from the host
- [ ] Can state which network mode breaks a multi-node lab, and why

**Cards touched** — CP-13

## B3 · Namespaces, veth pairs, bridges — build two routers by hand

**The most important day in the block.** Time-box the reading hard; the value is entirely in the terminal.

**Why this day exists**
containerlab, Docker, and every NOS container are the same three kernel primitives with a YAML file on top. Once you have built the topology by hand, `clab deploy` stops being magic and starts being a shortcut — and when it fails, you know which layer to look at.

**Objective**
*Say out loud:* what makes two namespaces joined by veth pairs *route* rather than *switch*, naming the exact thing you enabled.

**Source — 25 min. Stop reading at 25 minutes even if unfinished.**

| Time | What | Where |
|---|---|---|
| 15 min | `man ip-netns` — `add`, `exec`, `list`, and the note about where namespace files live | `man ip-netns` |
| 10 min | `man ip-link`, the `veth` and `bridge` type sections | `man ip-link` |

**Do — 65 min**

Build `h1 --- r1 --- r2 --- h2`. Four namespaces, three links, two routers, ping end to end.

1. Namespaces: `for n in h1 r1 r2 h2; do ip netns add $n; done`
2. Three veth pairs, one per link. Name both ends after the link so `ip -br link` is readable later:
   ```
   ip link add h1r1 type veth peer name r1h1
   ip link add r1r2 type veth peer name r2r1
   ip link add r2h2 type veth peer name h2r2
   ```
3. Move each end into its namespace: `ip link set h1r1 netns h1`, and so on for all six.
4. Address every interface. Use `/30`s from `192.0.2.0/24` (RFC 5737 — see [`docs/addressing-plan.md`](../docs/addressing-plan.md); start as you mean to continue). Bring every interface **and** `lo` up inside each namespace.
5. Ping `r1` from `h1`. It works. Ping `h2` from `h1`. **It does not.** Stop here and predict why before continuing — two separate reasons, and you need both.
6. Fix reason one: `ip netns exec r1 sysctl -w net.ipv4.ip_forward=1`, same on `r2`. **This is the answer to the objective.** Without it the namespaces have interfaces in two subnets and refuse to move packets between them.
7. Fix reason two: the hosts need routes. Default route on `h1` via `r1`, on `h2` via `r2`. And `r1` needs a route to `h2`'s subnet via `r2`, and vice versa. You have just hand-built what an IGP will do for you at B5 — remember this feeling at B8.
8. `ip netns exec h1 ping <h2>` — end to end.
9. Now watch it: `ip netns exec r2 tcpdump -ni r2r1 icmp` while pinging. You are seeing transit traffic on a router you built out of nothing.
10. **Then switch instead of route.** Add a fifth namespace with a bridge (`ip link add br0 type bridge`), put two veth ends into it, and put both attached hosts in the *same* subnet. Ping works with `ip_forward=0`. Say out loud what changed.

**Done when**
- [ ] `h1` pings `h2` across two hand-built routers
- [ ] You can name the sysctl and the routes as two *separate* requirements
- [ ] The bridge case works without forwarding enabled, and you can explain that difference
- [ ] The whole thing is in a shell script in `tools/`, committed, and it runs from clean

That script is worth committing even though it will never be used again. It is the cheapest possible proof to a future interviewer that you know what a router is at the kernel level.

**Cards touched** — CP-12

## B4 · Install containerlab

**Why this day exists**
Everything from B5 to D95 deploys with one command. Today that command starts working.

**Objective**
*Say out loud:* where containerlab puts the veth pairs and namespaces you built by hand yesterday.

**Source — 25 min**

| Time | What | Where |
|---|---|---|
| 10 min | Install page — read the prerequisites *before* running the installer | https://containerlab.dev/install/ |
| 15 min | Topology file reference — `topology`, `nodes`, `links`, `kind`, `image` | https://containerlab.dev/manual/topo-def-file/ |

**Do — 65 min**

1. Install. Confirm with `containerlab version`.
2. Write your first topology by hand — no generator. Two Alpine nodes, one link:
   ```yaml
   name: b4-first
   topology:
     nodes:
       n1: { kind: linux, image: alpine:latest }
       n2: { kind: linux, image: alpine:latest }
     links:
       - endpoints: ["n1:eth1", "n2:eth1"]
   ```
3. `containerlab deploy -t b4-first.clab.yml`. Read the summary table it prints.
4. **Now connect it to B3.** On the host: `ip -br link | grep -i veth` and `docker ps`. Find the veth pairs clab created. Use `nsenter` from B2 to read the interfaces from the host side. It is doing exactly what your script did.
5. Address `eth1` on both nodes manually and ping across. Note that clab created the link but not the addressing — that is deliberate, and for real NOS kinds the config comes from a startup file.
6. `containerlab inspect`, then `containerlab destroy -t b4-first.clab.yml --cleanup`. Confirm the veths are gone.
7. `git status`. The `clab-b4-first/` directory must be ignored. If it is not, fix `.gitignore` today, not at B6 when it contains a 2 GB image.

**Done when**
- [ ] A hand-written topology deploys and destroys cleanly
- [ ] The clab-created veth pairs located from the host using B1/B3 commands
- [ ] `git status` clean after a deploy — no `clab-*` directory staged

## B5 · First real lab — FRR, OSPF, then break it

**Why this day exists**
The first day a routing protocol runs in your lab. More importantly, the first day you break one on purpose. The breakage table you build today is the template for D13 and D27.

**Objective**
*Say out loud:* the four conditions that must match for an OSPF adjacency to reach Full, and the symptom of each when it doesn't.

**Source — 30 min**

| Time | What | Where |
|---|---|---|
| 15 min | FRR OSPF configuration — `router ospf`, `network`, `ip ospf` interface commands | https://docs.frrouting.org/en/latest/ospfd.html |
| 15 min | FRR in containerlab — the `linux` kind with the FRR image, and mounting a config file | https://containerlab.dev/manual/kinds/ |

**Do — 60 min**

1. Two-node topology, FRR image (`quay.io/frrouting/frr:latest`), one p2p link, loopbacks on both.
2. OSPF area 0 on the link and both loopbacks. `show ip ospf neighbor` until state is `Full`.
3. Confirm the loopbacks are in each other's RIB: `show ip route ospf`. Ping loopback to loopback.
4. **Break it four ways.** One at a time, revert between each. For every one, record the *symptom* and the *show command that revealed it*:

   | Break | Set it by |
   |---|---|
   | Hello/dead timer mismatch | `ip ospf hello-interval 5` on one side only |
   | Area mismatch | move one interface to area 1 |
   | MTU mismatch | `ip link set mtu 1400` on one side |
   | Network type mismatch | `ip ospf network broadcast` on one side, `point-to-point` on the other |

   The MTU one is the important one — the adjacency hangs in `ExStart`/`Exchange` rather than failing cleanly. You will meet this again at D13 with IS-IS, where it behaves differently and worse.
5. Commit the breakage table to `00-journal/2026-08.md`. Four rows, three columns.

**Weekend extension**
`tcpdump` the link and capture a Hello. Find the hello interval, the area ID, and the neighbour list *inside the packet*. Seeing the adjacency state machine on the wire rather than in a `show` command is worth an hour.

**Done when**
- [ ] Adjacency reaches Full, loopbacks reachable
- [ ] Four breakages performed, each with symptom and diagnosing command recorded
- [ ] The MTU case identified as behaving differently from the other three, in writing
- [ ] Topology file committed to `01-igp-core/`

**Cards touched** — CP-14 (armed, not yet due)

## B6 · Pull vendor images

**Why this day exists**
The plan assumes Junos and one other NOS from B39 onward. Image acquisition is an admin task with licensing friction, and it will eat a session whenever you do it — better now than at B40 when the capstone is waiting.

**Objective**
Two different vendor NOSes boot in containerlab on your machine, and you know which ones your hardware cannot run.

**Source — 30 min**

| Time | What | Where |
|---|---|---|
| 10 min | containerlab supported kinds — the definitive list of what works and what each needs | https://containerlab.dev/manual/kinds/ |
| 20 min | SR Linux quickstart — the one NOS with no account wall | https://learn.srlinux.dev/ |

**Do — 60 min**

1. **Nokia SR Linux first.** Publicly pullable, no registration. Deploy a single node, log in, `show version`. This guarantees you finish the day with at least one vendor NOS working.
2. **Then the account-walled ones**, in priority order for this plan:
   - **Juniper vJunos-router** — the plan's primary target (B39, B40, D20, D21). Free account required. **Check your hardware first: it needs KVM and several GB of RAM per node.** If `kvm-ok` fails or you are on a VM without nested virtualisation, find that out today.
   - **Arista cEOS** — free account, lightweight, boots fast. Excellent fallback for topology work when vJunos is too heavy.
   - **Cisco XRd** — needs an account and specific host sysctls. If it fights you, note it and move on: `docs/resources.md` already flags Cisco Modeling Labs free tier as the D21 escape hatch.
3. For each image that boots, record in the journal: RAM per node, boot time, and the maximum node count your machine will take. **This number sets what D91's five-AS capstone can actually be.** Find out in August, not December.
4. `git status`. Then `git ls-files | grep -iE '\.(qcow2|tar|iso)$'` — must return nothing. The CI check in `.github/workflows/check.yml` enforces this, but catch it locally first.

**Done when**
- [ ] SR Linux boots and you can log into it
- [ ] At least one of vJunos / cEOS / XRd boots, or a written note on exactly why it can't and what the fallback is
- [ ] Max node count for your machine recorded in the journal
- [ ] No image blobs in `git ls-files`

**If vJunos will not run on your hardware**, decide the substitute today and write it in the journal: cEOS for topology-heavy days, and CML free tier or a cloud VM rented by the hour for the specific Junos days (B39, B40, D20). Do not leave this unresolved — the plan names Junos in six places.
